# ADR-0010: Versioned release manifest for contracts, bindings, events, and deployments

- **Status:** Proposed
- **Date:** 2026-08-18
- **Deciders:** Lafiya contract maintainers

## Context

[Issue #135](https://github.com/Lafiya-xyz/Lafiya-contract/issues/135) asks how contract
wasm, generated bindings, event schemas, deployed contract IDs, and downstream consumers
should be versioned and released as one compatible unit. Today the pieces exist but are
not bound together:

- `Cargo.toml` carries a single `[workspace.package]` SemVer (`docs/releasing.md`), but
  every contract crate shares it — there is no per-artifact version.
- `CHANGELOG.md` records what changed, in prose, for humans.
- `bindings/*/package.json` each hardcode `"version": "0.0.0"` — binding versions are not
  actually cut alongside a contract release (`docs/typescript-bindings.md`,
  `PUBLISHING.md`).
- `config/networks.toml` records the *current* contract ID per network, but not the wasm
  hash it corresponds to, when it was deployed, or what it superseded.
- `docs/runbooks/contract-upgrade.md` defines a rigorous three-way wasm-hash verification
  process (reviewer / operator / network) for a *single* upgrade, but nothing carries that
  verified hash forward into a durable, cross-repo-readable record.
- Each contract already tracks its own on-chain storage-schema version
  (`SCHEMA_VERSION` / `get_schema_version()`, see the runbook), and emits `#[contractevent]`
  structs (`AttesterAdded`, `AttestationRecorded`, `Upgraded`, ...), but nothing declares
  which binding/consumer version a given event shape is compatible with.

A contract upgrade can simultaneously change methods, event shapes, storage layout, and
deployed addresses. Without one artifact that binds these together per release, a consumer
(`lafiya-web`, `lafiya-verifier`) has no reproducible way to check "is the binding I have
compatible with the contract instance I'm calling" other than reading source by hand.

This ADR is the requested spike output: a release manifest schema, a compatibility policy,
a prototype CI workflow, an artifact-hash/deployment-record format, and a rollout/rollback
recommendation. It defines the artifact and the policy; it does not change contract
behavior and does not yet wire enforcement into required CI (see "Follow-up").

## Decision

### 1. A generated release manifest, not a hand-maintained one

Adopt a JSON **release manifest**, schema at
[`docs/release-manifest/schema.json`](../release-manifest/schema.json) (`manifest_version: 1`),
generated by [`scripts/generate_release_manifest.py`](../../scripts/generate_release_manifest.py)
from things that are already sources of truth, rather than asking a human to hand-author
and keep it in sync:

| Manifest field | Derived from |
| --- | --- |
| `release.workspace_version` | `[workspace.package].version` in `Cargo.toml` |
| `release.git_commit` / `git_tag` | `git rev-parse HEAD`, `git describe --tags --exact-match` |
| `contracts[].storage_schema_version` | the contract's `SCHEMA_VERSION` const (`contracts/*/src/lib.rs`) |
| `contracts[].wasm.sha256` / `size_bytes` | `target/wasm32v1-none/release/*.wasm`, built with `--optimize=false` per the upgrade runbook §3 |
| `bindings[].package_version` / `generated_from_wasm_sha256` | `bindings/*/package.json` and the contract's own `wasm.sha256` |
| `events[]` | every `#[contractevent] pub struct` in each contract, parsed from source: `#[topic]`-annotated fields vs. data fields |
| `deployments[]` | `config/networks.toml` (today: current pointer only — see the gap called out in "Deployment promotion records" below) |

Because it's generated from source and build output, the manifest can't drift from the
code the way a hand-maintained document would — regenerating it is the verification step.
[`scripts/validate_release_manifest.py`](../../scripts/validate_release_manifest.py) checks
the result against the JSON Schema and one cross-field invariant the schema alone can't
express: every `bindings[].generated_from_wasm_sha256` must equal its contract's
`wasm.sha256`, or the committed binding is stale relative to the wasm it claims to wrap.

A worked example, generated from this repository's current (pre-alpha, undeployed) state:
[`docs/release-manifest/examples/v0.1.0-dev.json`](../release-manifest/examples/v0.1.0-dev.json).
It is not a real release — no contract has been deployed to any network yet (every
`config/networks.toml` contract ID is still empty) — but it demonstrates the full shape,
including `wasm.sha256: null` and `deployments[].status: "not_deployed"`, which is the
honest state of an unbuilt, undeployed pre-alpha checkout.

### 2. Compatibility policy

Three independent version axes exist per contract, and each has its own compatibility rule:

| Axis | Compatible (minor/patch) change | Breaking (major) change |
| --- | --- | --- |
| **Public API** (`#[contractimpl]` functions) | Add a new function; add an optional/defaulted parameter in a way SDK client codegen tolerates | Remove/rename a function; change a parameter type or order; change a return type; change `require_auth` semantics |
| **Storage schema** (`SCHEMA_VERSION`) | Append-only: new `DataKey` variant or new struct field per the runbook's storage-versioning strategy (§1, developer summary) | Any reorder/removal/renumbering of existing `DataKey` variants or struct fields (forbidden outright — not just "breaking", actually corrupts reads) |
| **Events** | New event; new *data* field on an existing event (see `classify_events` in the generator: data fields may grow, since well-behaved decoders read by name) | New/removed/reordered `#[topic]` field on an existing event (topics are positional and part of the event's on-chain identity — `AttestationRegistry`/`AttesterRegistry` conventions treat them as ABI, see `contracts/*/src/lib.rs`); event removed |

The generator classifies each event automatically against a `--previous` manifest
(`events[].compatibility`: `new` / `compatible` / `breaking` / `removed`); API and storage
classification is not automated by this spike (see "Follow-up") but the rule above is the
policy a human (or a later CI check) applies.

**Contract SemVer, concretely:** `workspace_version`'s major/minor/patch meaning is the
*union* of the three axes above — a release is only a patch/minor if every one of API,
storage, and events it changed individually qualifies as compatible; a major bump is
required if any one of them is breaking. This matches `docs/releasing.md`'s existing
policy text but makes it mechanically checkable instead of only reviewer-judgment.

### 3. Compatibility matrix (what requires bumping what)

| Change | Contract version | Binding version | Deployment action |
| --- | --- | --- | --- |
| Doc/comment only, no wasm change | patch | none | none |
| New event, new optional storage field, new function | minor | minor (regenerate) | code-only `upgrade()` |
| Breaking API/event/storage change | major | major (regenerate) | `upgrade()` + `migrate()` (runbook §5) |
| Same contract version, wasm re-optimized differently | — | — | not applicable: the runbook requires `--optimize=false` precisely so the reviewed/operator/uploaded hash never diverges for the same source |

Bindings are versioned independently (`PUBLISHING.md`) but this manifest is what lets a
binding declare, verifiably, which contract wasm hash it was generated from
(`generated_from_wasm_sha256`) — closing the gap where `bindings/*/package.json` today says
`"0.0.0"` regardless of which contract revision produced it.

### 4. Artifact hash and deployment-record format

The manifest's `contracts[].wasm` object *is* the artifact-hash record: `sha256` of the
`--optimize=false` build, matching exactly what `docs/runbooks/contract-upgrade.md` §3
calls `H_reviewed` / `H_operator` / `H_uploaded`. A manifest generated in CI from a clean,
locked build is a fourth independent computation of the same hash, on top of the runbook's
existing three-way check.

The `deployments[]` array is the proposed deployment-record format: one entry per
`(network, contract)`, with `contract_id`, `wasm_sha256`, `storage_schema_version`,
`deployed_at`, `upgrade_tx`, and `previous_wasm_sha256` (the rollback target). **This spike
does not populate most of those fields today** — `config/networks.toml` only ever stores
the *current* contract ID, not a history, so `wasm_sha256`/`deployed_at`/`upgrade_tx` are
honestly emitted as `null` with a `source` field saying so (see the generator's
`build_deployments`). Populating them for real requires `scripts/deploy.sh` and
`scripts/upgrade.sh` to append a record each time they run — that's the follow-up work this
spike scopes but does not implement (see "Follow-up").

### 5. Recommended rollout and rollback process

This does not replace `docs/runbooks/contract-upgrade.md` — it adds one artifact to it:

- **Rollout:** after runbook §2 item 5 (expected hash computed and shared), generate a
  release manifest from the same clean build and commit/attach it alongside the release tag
  (e.g. as a release asset, mirroring how `PUBLISHING.md` already proposes tagging triggers
  binding publication). A consumer repo runs
  `scripts/check_manifest_compatibility.py <manifest> <its requirements file>` in its own CI
  before bumping its pinned contract/binding version — see
  [`docs/release-manifest/examples/lafiya-web.requirements.json`](../release-manifest/examples/lafiya-web.requirements.json)
  for the worked example, which passes against `v0.1.0-dev.json` above and fails loudly
  (exit 1, itemized reasons) if a required `min_storage_schema_version` isn't met.
- **Rollback:** runbook §6 already makes rollback a second `upgrade()` call with the
  previous wasm hash. Once `deployments[].previous_wasm_sha256` is populated (see
  Follow-up), a rollback script can read it directly from the manifest instead of an
  operator having to locate the prior release's build output by hand. The runbook's
  existing caveat stands unchanged: rollback restores code, not a post-`migrate()` storage
  shape — prefer roll-forward once a migration has run (§6).

### 6. Release ownership across repositories

- **`lafiya-contract`** (this repo) owns: cutting the SemVer, running `make wasm` +
  `make bindings`, generating and validating the release manifest, and publishing it
  (attached to the git tag, per `docs/releasing.md` §2). It does not own or gate on any
  consumer's compatibility requirements file.
- **`lafiya-web`, `lafiya-verifier`** each own their own `*.requirements.json` (the schema
  demonstrated by the `lafiya-web` example here) and are responsible for running
  `check_manifest_compatibility.py` in their own CI against the manifest of whichever
  release they intend to pin. They do not gain write access to this repo's manifest.
- **`lafiya-docs`** owns rendering the manifest/compatibility policy into human-facing
  release notes; it consumes the manifest as data, same as any other downstream repo.
- **Bindings publication** (npm, per `PUBLISHING.md`) remains this repo's responsibility,
  triggered off the same tag the manifest is generated from, so `bindings[].package_version`
  in the manifest and the published npm version never disagree.

## Alternatives considered

### Hand-maintained release notes only (status quo, extended)

Keep `CHANGELOG.md` as the sole release record and just ask authors to note
API/storage/event impact in prose more consistently.

Rejected as the primary mechanism: prose is not machine-checkable, so a consumer still has
no way to *verify* compatibility before integrating, only to *read about* it. It remains
valuable as the human-readable companion to the manifest and is kept.

### A single monolithic version for contracts + bindings + deployments

Bump one version number for the whole repository and require every consumer to track it
exactly.

Rejected: contracts, bindings, and per-network deployments legitimately move at different
cadences (a binding regeneration with no contract change, or a testnet deployment of a
version not yet promoted to mainnet). Collapsing them into one number either forces
lockstep releases for unrelated changes or lies about what actually changed. The manifest's
multi-axis structure keeps them independently inspectable while still relating them through
`generated_from_wasm_sha256` and `deployments[].wasm_sha256`.

### Consumer compatibility enforced by a shared package/SDK version pin only

Rely on `lafiya-web` pinning an exact bindings npm version and trust that's sufficient.

Rejected as the sole mechanism: a version pin says *which* bindings a consumer has, not
whether those bindings are compatible with the specific deployed contract instance it's
about to call (e.g. a stale binding pinned against a not-yet-migrated deployment). The
manifest's `deployments[]` + `check_manifest_compatibility.py` check the actual deployed
state, not just the binding version.

## Consequences

### Positive

- One reproducible, generated artifact answers "what contract/binding/event/deployment
  versions go together," closing the gap the issue identified.
- Artifact hashing reuses the runbook's existing `--optimize=false` discipline rather than
  introducing a second, possibly-divergent hashing process.
- The compatibility check is demonstrated end-to-end in this repo today (generate → validate
  → check), without requiring any other repository to exist or be modified first.
- Event compatibility classification is mechanical (field-set diff), removing one class of
  "looked fine in review, broke a decoder in production" incidents.

### Trade-offs and risks

- The manifest is only as trustworthy as the build that produced it; a manifest generated
  from a dirty or unlocked checkout can misreport hashes. CI should always generate it from
  a clean, `--locked` checkout of the tag (the prototype workflow does this).
- `deployments[]` is honestly incomplete today (see §4) — this spike defines the format
  without yet writing history into it. Until `deploy.sh`/`upgrade.sh` are extended (see
  Follow-up), the manifest's deployment section is not more informative than
  `config/networks.toml` already is.
- API-level breaking-change detection (as opposed to event/storage) is not automated by
  this spike; it still relies on the existing PR-review process and `docs/releasing.md`'s
  policy text.
- Consumers must opt in by writing and running their own requirements file; nothing in this
  repo enforces that a consumer actually checks compatibility before upgrading.

## Follow-up

- Extend `scripts/deploy.sh` and `scripts/upgrade.sh` to append a `deployments[]`-shaped
  record (contract_id, wasm_sha256, deployed_at, upgrade_tx, previous_wasm_sha256) to a
  persistent, append-only ledger per network, so the manifest generator can populate real
  deployment history instead of `null` placeholders.
- Wire `.github/workflows/release-manifest.yml` to run on the actual release tagging step in
  `docs/releasing.md` §2, and attach `release-manifest.json` as a GitHub release asset.
- Add automated public-API breaking-change detection (e.g. diffing `#[contractimpl]`
  function signatures the way `.github/scripts/check_readme_contracts.py` already parses
  them) and feed the result into `contracts[].compatibility`, mirroring what this spike did
  for events.
- Publish `lafiya-web`'s and `lafiya-verifier`'s real `*.requirements.json` files in their
  own repositories and wire `check_manifest_compatibility.py` (vendored or published as a
  small package) into their CI, replacing the illustrative copy in
  `docs/release-manifest/examples/`.
- Decide whether the manifest itself should be published to the `@lafiya` npm scope
  alongside bindings (per `PUBLISHING.md`) so consumers can `npm install` a specific
  manifest version rather than fetching a release asset.
- Revisit `bindings/*/package.json` versions (`docs/typescript-bindings.md`,
  `PUBLISHING.md`): they are hardcoded at `0.0.0` today; the first real release under this
  ADR should also start actually versioning them.
