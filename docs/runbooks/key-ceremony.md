# Runbook: Admin and Guardian Key-Generation Ceremony

**Audience:** ceremony lead, key holders, witnesses, and auditors.

**Scope:** creating, rotating, and recovering the ed25519 keys behind the two
`multisig-account` contracts that control the deployment:

| Account | Holds | Threshold policy |
| --- | --- | --- |
| **admin** | `admin` of `attester-registry` and `attestation-registry`: upgrades, allowlist, roles, unpause | `2 <= t < n`. Two people are always needed, and losing one key never locks the account. Production: **3-of-5**. |
| **guardian** | the `Guardian` role: `pause` only (ADR-0003, PAUSE-POLICY) | `1 <= t < n`. Pausing must be fast. Production: **1-of-3**. |

CHW attester keys follow a separate process:
[CHW key custody](../security/chw-key-custody.md). Every other control rests
on these two signer sets, so the procedure assumes any single person, device
or computer in the room may be dishonest or compromised.

**Tooling:** [`scripts/verify_signer_set.py`](../../scripts/verify_signer_set.py)
computes the signer-set hash during the ceremony and later checks a ceremony
record against the chain. Records (public data only) go under
[`docs/security/ceremonies/`](../security/ceremonies/). The first one is the
[testnet dry run](../security/ceremonies/2026-10-18-testnet-dry-run.md).

---

## 1. Roles

| Role | Who | Duty |
| --- | --- | --- |
| **Ceremony lead** | Release manager | Runs the script below and assembles the transactions. Holds no seat in the ceremony they lead. |
| **Key holders** | One person per seat | Generates and keeps one key. No one holds two seats, and no one holds both an admin and a guardian seat. |
| **Witnesses** | At least 2. At least one is independent of the core team (auditor or partner org). | Watch every step, read back and compare public keys and hashes, sign the witness record. |
| **Recorder** | A witness may do this | Writes the witness record (§6) with timestamps as the ceremony happens. |

At least one witness must be present for every step. If a key holder leaves
the room with their device before §4.6, that seat is regenerated.

## 2. Equipment and entropy

- **Key devices:** one new hardware wallet with a Stellar app per seat, bought
  by the key holder from the vendor directly, never second-hand. The key is
  generated by the device's own TRNG, on the device. Seeds are never typed
  into, photographed by, or displayed on a general-purpose computer.
- **Seed backups:** one metal backup per seat, sealed in a numbered
  tamper-evident bag. Each seat's backup is stored at a different site from
  its device.
- **Ceremony laptop:** boots a read-only live image whose SHA-256 was checked
  against the published value by two witnesses. It has no network until §4.7.
  It carries a pinned `stellar` CLI (same version as CI, hash checked) and
  this repository at the release tag.
- **Witness machines:** each witness computes the signer-set hash on their
  own machine. Agreement between machines rules out a tampered ceremony laptop.
- **Not permitted:** software-generated keys, brain wallets, cloud-synced
  passkeys, phones, or keys generated in advance of the ceremony.

## 3. Device checks (per seat, before generation)

1. Inspect the packaging and tamper seals. Record the device serial and the
   seal state.
2. Run the vendor's genuine-device check. Record the attestation result.
3. Record the firmware version and compare it with the vendor's published
   release notes.
4. Factory-reset the device on camera (or in front of both witnesses), even
   when it is new.
5. Any failure: the device is set aside, recorded, and replaced. Never "try
   again" on the same device.

## 4. Procedure

### 4.1 Preparation (at least 7 days before)

- [ ] Pick the ceremony id (`YYYY-MM-DD-<network>-<purpose>`), seats, thresholds, and venue.
- [ ] Two witnesses check the laptop image hash and the CLI binary hash.
- [ ] Print the witness record (§6), one copy per witness.
- [ ] Have the current admin contract ids from `config/networks.toml` (rotation only).

### 4.2 Opening

- [ ] Recorder notes the time, attendees, and ID checks.
- [ ] Everyone turns phones off and puts them away. Recording, if used, points at hands and devices, never at seed words.

### 4.3 Device checks

- [ ] §3 done for every seat and recorded.

### 4.4 Key generation (per seat)

1. The key holder generates the key on the device and writes the backup to
   the metal plate out of everyone's sight (witnesses watch the person, not
   the words).
2. The key holder confirms the backup on the device, then seals it in the
   numbered bag. The recorder notes the bag number.
3. The device shows the `G...` public key. The key holder reads it aloud. A
   witness types it into their own machine. The lead types it into the
   ceremony laptop. Both run:

   ```bash
   scripts/verify_signer_set.py hash --threshold 2 G...   # one key: catches typos via the checksum
   ```

### 4.5 Signer-set hash

On the ceremony laptop and on each witness machine, independently:

```bash
scripts/verify_signer_set.py hash --threshold <t> <G... for every seat>
```

All hashes must match. The recorder writes the hash in the witness record,
and each witness initials it.

### 4.6 Close of generation

- [ ] Devices go back to their key holders. Backup bags go to the custodian for each storage site.
- [ ] The recorder notes every bag number and storage site.

### 4.7 On-chain configuration

The ceremony laptop now goes online. Every transaction it assembles is
checked by a witness before anyone signs.

- **New deployment:** deploy `multisig-account` with
  `--signers '[<hex keys>]' --threshold <t>`, then deploy the registries with
  the admin account as constructor `admin`. Their constructors require the
  admin account's authorization: collect `t` signatures with
  [`@lafiya/multisig-auth`](../../packages/multisig-auth/README.md) ceremony
  files. Then grant `Guardian` to the guardian account through
  `grant_role(Guardian, <guardian account>)`, signed by admin.
- **Existing deployment:** see the [admin key rotation runbook](admin-key-rotation.md).

### 4.8 Verification and record

1. Write the record JSON next to the previous ones in
   `docs/security/ceremonies/`: contract ids, thresholds, seats with public
   keys, the signer-set hash, and which registries each account must control.
   **Public data only.**
2. Two witnesses, each on their own machine and RPC provider, run:

   ```bash
   scripts/verify_signer_set.py verify docs/security/ceremonies/<id>.json --source <any funded G...>
   ```

   Every check must pass: the on-chain signer set equals the record, the
   threshold matches, the policy is plain `t`-of-`n`, the hash recomputed from
   chain matches, every registry's `get_admin` is the admin account, and the
   guardian account holds `Guardian`.
3. Commit the record and a transcript (`<id>.md`: steps, timestamps,
   transaction hashes, verification output, signed-off witness names) in a
   PR. Reviewers re-run step 2.

## 5. Rotation and recovery

### 5.1 Planned rotation

Rotate a seat when its holder leaves, when its device reaches end of support,
and at least every 24 months. Run §3 to §4.5 for the new seat only, then
follow the [admin key rotation runbook](admin-key-rotation.md). The old
device is factory-reset and destroyed in front of a witness. Its backup bag
is retrieved, opened in front of a witness, and destroyed. Record both.

### 5.2 Compromised or suspect ceremony

Treat a ceremony as suspect if any of these happens: a device check failure
found afterwards, a broken or missing backup seal, seed words possibly
observed or recorded, ceremony software found tampered, a verification
mismatch, or a key holder under coercion.

| Suspect keys | Response |
| --- | --- |
| **Fewer than `t`** (control intact) | Within 24 hours: run a new ceremony for the suspect seats only, then `set_signers` signed by `t` unaffected keys. Raise watchdog paging to high severity until the rotation is verified. |
| **`t` or more admin keys** (attacker may control admin) | Immediately: a guardian pauses both registries. Watch for `upgrade`, `propose_admin`, and role events ([watchdog runbook](watchdog.md)). If enough honest keys remain, rotate at once. If not, treat the deployment as lost: run a fresh ceremony, deploy new contracts, migrate clients through `config/networks.toml`, and publish the old contract ids as untrusted ([security triage](security-triage.md)). |
| **`t` or more guardian keys** | Admin revokes `Guardian` from the guardian account, then runs a new guardian ceremony and grants the role to the new account. An attacker with guardian keys can only pause; admin can unpause. |
| **Witness record or transcript wrong** | Re-run §4.8 verification. If the chain matches the intended keys, correct the record in a PR that says why. If not, treat it as the row above that applies. |

Every recovery ends with a new record in `docs/security/ceremonies/` that
links to the one it replaces.

## 7. Auditor checklist

- [ ] Every seat has a separate holder. No one holds two seats, and no one holds both an admin and a guardian seat.
- [ ] Thresholds meet policy (admin `2 <= t < n`, guardian `1 <= t < n`). `verify` checks this.
- [ ] Every key came from a device TRNG on a device that passed §3. Serials and firmware are recorded.
- [ ] Every seed backup was sealed, bag numbers are recorded, and backups are stored at a different site from their devices.
- [ ] The signer-set hash was computed on at least two independent machines and initialled.
- [ ] The committed record passes `scripts/verify_signer_set.py verify` against the chain today.
- [ ] Every registry's `get_admin` is the admin account, and the guardian account holds `Guardian`.
- [ ] The transcript contains no secret material: no seeds, secret keys, or unredacted backup photos.
- [ ] Rotations and recoveries since the last audit each have a record and a transcript.
- [ ] Deviations are recorded with a reason.
